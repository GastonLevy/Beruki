# Architecture

## Application Boundaries

Beruki keeps the Symfony backend and Angular frontend separated. Backend code owns persistence, domain behavior, application services, authentication, and API contracts. Frontend code owns navigation, presentation, user interaction, and API consumption.

Controllers should stay thin. They may validate request shape, call repositories or services, and return responses, but reusable application logic belongs in services. Repositories are responsible for data access and persistence queries. Entities are responsible for their own state and domain invariants, and must not contain infrastructure concerns such as database lookups, external API calls, or random identifier generation.

Changes should stay small and focused. Avoid unrelated refactors, duplicated logic, premature abstractions, and extra interfaces/factories/managers unless they remove real complexity or support an immediate need.

## Customer Identity

`Customer.id` is an internal Doctrine/database identifier. It remains the primary key for relations and persistence, and admin-only screens may use it when they operate inside EasyAdmin or other internal tooling.

`Customer.customerCode` is the public customer identifier. Public customer API routes and collector-facing frontend navigation use `customerCode`, not the numeric Doctrine ID. The code is unique, non-sequential, generated by `App\Service\CustomerCodeGenerator`, and immutable after assignment. It is not an authentication credential.

`Customer` enforces value-level rules for `customerCode`: valid format and immutability after assignment. It does not generate codes and does not query the database. `CustomerRepository` exposes customer lookups and existence checks only. Code generation and collision retry logic live in `CustomerCodeGenerator` so manual creation, future imports, and any other creation flow can reuse the same behavior.

`Customer.fullName` may be `null`. This supports future imports where the router queue name must not be treated as the customer's real name.

`Customer` contains customer/person/subscriber data only. Technical network data does not belong to `Customer`.

## Customer Connections

`CustomerConnection` represents a technical connection owned by a customer. A customer may have zero, one, or many connections. Initial connection data includes nullable unique `serviceIp`, nullable `macAddress`, active state, and creation time.

IP, MAC, MikroTik, queue, ONU, OLT, interface, and other technical network state belong to `CustomerConnection` or future technical entities, not to `Customer`, `Plan`, or `CustomerPlan`. `CustomerPlan` represents the commercial relationship between a customer and a plan. For now, `CustomerConnection` and `CustomerPlan` both belong directly to `Customer`; only relate a specific connection to a plan later if a real functional need appears.

Connection queries belong in `CustomerConnectionRepository`. Future network integrations should query by `CustomerConnection.serviceIp` and must not assume one IP per customer.

## Future MikroTik Integration

The first MikroTik integration should be read-only from the router perspective. RouterOS access must be isolated in services, never called directly from controllers or entities.

The initial import should create or match customers and connections idempotently:

```text
MikroTik /queue simple
        -> target
        -> CustomerConnection.serviceIp
```

It should use `queue.target` as `CustomerConnection.serviceIp` after removing `/32`, avoid duplicates by looking up `CustomerConnection` by `serviceIp`, leave `Customer.fullName = null`, ignore `queue.name`, and reuse existing customer creation services, including `CustomerCodeGenerator`.

MikroTik credentials and connection details must come from configuration or environment variables. Do not hardcode IP addresses, usernames, passwords, or ports. Future synchronization must not modify MikroTik unless a task explicitly asks for write behavior.

## Git Flow

The project flow is:

```text
feature/fix branch -> develop -> main
```

New tasks should start from `develop` and use a descriptive branch. Do not work directly on `main`. Do not merge automatically at the end of a task, and do not push unless explicitly requested. Run relevant backend/frontend validations before proposing a merge.
