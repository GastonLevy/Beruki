# Project Rules

Before implementing a future task, read this file and follow these rules unless the task explicitly says otherwise.

## General

- Keep controllers thin.
- Put reusable application logic in services.
- Keep queries and persistence access in repositories.
- Keep entities limited to state and their own domain behavior.
- Do not put infrastructure logic in entities.
- Avoid duplicated logic; reuse existing services first.
- Keep changes small and focused.
- Do not refactor outside the task scope without a clear need.
- Avoid overengineering.
- Do not create interfaces, factories, or managers unless they add real value.
- Keep Symfony backend and Angular frontend responsibilities separated.
- Do not hardcode secrets or credentials.
- Review `.env` before versioning sensitive changes.

## Customer

- `Customer.id` is internal for Doctrine, relations, and database use.
- `customerCode` is the public customer identifier.
- Do not expose the numeric customer ID unnecessarily to collectors.
- `customerCode` is unique, immutable, and generated by `CustomerCodeGenerator`.
- Repositories do not generate identifiers.
- `fullName` may be `null`.
- Technical connection data does not belong to `Customer`.
- A customer can have multiple `CustomerConnection` records.
- IP and MAC belong to `CustomerConnection`.
- `CustomerPlan` represents commercial plan assignment.
- `CustomerConnection` represents technical network connection data.

## Future MikroTik Integration

- The first MikroTik integration is read-only from the router perspective.
- Isolate RouterOS access in services.
- Never call RouterOS directly from controllers.
- Customer creation must reuse existing services.
- Do not store `queue.name` as `fullName`.
- In the initial import, set `fullName = null`.
- Use `queue.target` for `CustomerConnection.serviceIp`, removing `/32`.
- Avoid duplicates by looking up `CustomerConnection` by `serviceIp`.
- Network integrations must work through connections and not assume one IP per customer.
- Read MikroTik credentials from configuration or environment variables.
- Do not hardcode IP, username, password, or ports.
- Importers must be idempotent.
- Future sync must not modify MikroTik unless explicitly requested.

## Git Flow

- Use `feature/fix branch -> develop -> main`.
- Start new tasks from `develop`.
- Create a descriptive branch.
- Do not work directly on `main`.
- Do not merge automatically after a task.
- Do not push unless explicitly requested.
- Run validations before proposing a merge.
